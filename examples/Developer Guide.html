BMO SharePoint design system

Developer guide — start here

How this design system is put together, what it gives you, and how to build BMO SharePoint apps with it in Alpine and plain HTML.

Audience: front-end developers Stack: Alpine.js + HTML + CSS Tokens: colors_and_type.css
Orientation

What a design system is here

This isn't an installable package you npm install and import components from — it's a lighter shape: design tokens, ready-made CSS classes, and guidance, linked straight into the page.

This system is three things: tokens, a component layer, and guidance. It ships the decisions — every color, size, space, radius, shadow, and motion value — as CSS custom properties in colors_and_type.css; a set of ready, token-built component classes in components.css (buttons, inputs, cards, badges, tabs, data grids, dialogs…); plus written rules and reference pages for combining them. You write plain markup, add a class, and it looks like BMO.

One sentence: link two stylesheets — colors_and_type.css (tokens) then components.css (classes) — write HTML, and wire behaviour in Alpine. No npm, no build step. Components.html renders every class with copy-paste markup.

Why this shape? Because these apps are embedded inside Microsoft SharePoint Online, where the production stack is Alpine.js and plain HTML/CSS, with no build pipeline. Two <link> tags drop the whole system into that environment.

Authoring a component

A component here is a CSS class on plain HTML — not an imported widget. You write the element and apply the system's classes, which are built from tokens, so it renders on-brand. You keep full control of the markup, and there's nothing to install.

Author the element, apply system classes
<!-- a component is a class on plain HTML -->
<button class="btn btn--primary"
        x-on:click="submit()">
  Submit request
</button>

<!-- .btn ships in components.css, built once from tokens -->

The key discipline: never hard-code a value the system already names. No #0079C1 in your CSS — use var(--accent-rest). No padding: 15px — use the 4px ramp. When you do that, every screen stays consistent and a future token change propagates everywhere for free.

What's in the box

Everything is plain files in this project — no registry, no install. Here's what each one is for.

colors_and_type.css
The tokens. All design tokens (color, type, spacing, radius, shadow, motion), drop-in element defaults (h1–h6, p, a), and opt-in utility classes (.imgph, .lift, .reveal). Link this first.
components.css
The component layer. Token-built classes for every pattern — .btn, .input, .field, .card, .badge, .tabs, .msgbar, .grid, .dialog, and more. Link this second.
styles.css
One-tag bundle. @imports the two files above in the right order — link this instead if you prefer a single tag.
bmo-icons.svg
The icon sprite. 37 Fluent symbols, ids ic-fluent-{name}-24-regular. Inline it once per page; reference with <use href="#ic-fluent-…">. Do not rename or re-curate.
fluent-icon.js
Optional icon element. One script tag enables <fluent-icon name="home-24-regular"> — the sugar form over the same sprite. The no-JS <use> form needs none of this.
Components.html

What's not here

Knowing the edges saves you searching for things that don't exist.

  • No npm package, no import, no build step. You will not import anything from this system. You link two stylesheets and write markup.
  • No framework components. There's no imported <Button> component and no web-component library (e.g. Web Awesome). A component here is a CSS class on plain HTML: <button class="btn btn--primary">. They ship in components.css.
  • No JavaScript behaviour baked in. The classes style; they don't behave. Wire interactivity yourself in Alpine (x-data, x-on, x-show, x-model).
  • No licensed BMO logo or photography. The logo is a placeholder; imagery uses labeled .imgph placeholders until real assets are licensed.
  • No dark mode and no theming switch. One light theme, tuned for the SharePoint shell.
Using it

Consume the system

Step one on any page: link the system and Alpine. One <link> to styles.css pulls in every token, the styled base elements, and the component classes; Alpine drives behaviour. That's the whole runtime — no build. (Prefer the layers? Link colors_and_type.css then components.css instead — same result.)

In your SharePoint page / web part
<!-- one file: tokens + base elements + component classes -->
<link rel="stylesheet" href="styles.css">
<script defer src="https://unpkg.com/alpinejs@3/dist/cdn.min.js"></script>
<!-- CDN shown for brevity; self-host alpine.min.js in SiteAssets for production -->

<!-- base elements already styled — no classes needed -->
<h1>Expense & approvals</h1>      <!-- H1, Regular weight, Slate -->
<p>Submit a claim and track approvals.</p>
<a href="#">Review the policy</a>      <!-- Accessible Blue link -->

From there, reference tokens with var(--token) anywhere you need a value — in a stylesheet, in a style attribute, or in an Alpine :style binding:

Three ways to apply a token
/* 1 · in CSS */
.summary { color: var(--fg-secondary); padding: var(--space-200); }

<!-- 2 · inline style -->
<div style="border-radius:var(--radius-large);box-shadow:var(--shadow-4)">…</div>

<!-- 3 · Alpine binding -->
<span :style="isOverdue ? 'color:var(--fg-danger)' : 'color:var(--fg-success)'">…</span>
Rule of thumb: if you're about to type a hex code, a pixel value, or a shadow by hand, stop — there is almost certainly a token for it. Raw values are how a design system rots.

Token layers — reach for the semantic one

Tokens come in three layers. Build against the semantic layer; it's the stable contract. The raw layers underneath can change without breaking your code.

LAYER 1 · RAW BRAND
Brand + Fluent values
Literal BMO and Fluent 2 values. Rarely reference directly.
--bmo-blue: #0079C1
--f2-grey-96: #F5F5F5
LAYER 2 · SEMANTIC ROLE
What it's for ✓
Names a job, not a color. This is your layer.
--fg-primary
--accent-rest
--surface-canvas
LAYER 3 · SCALES
Spacing · radius · shadow · motion
Numeric ramps. Use the step, never an off-ramp value.
--space-160 (16px)
--radius-large (8px)
--motion-normal

So: color: var(--fg-primary) — not var(--bmo-slate), and certainly not #001928. If a semantic token exists for your purpose, it wins, because it carries the intent and survives a re-theme.

Use a component

These classes ship in components.css — you don't write them, you use them. Below is what each one is made of (all tokens, no magic) plus the markup to copy. Every class is rendered with copy-paste markup in Components.html. Need one that's missing? Author it the same way, on tokens only.

Button

/* ships in components.css — here's what it's made of */
.btn{
  font: var(--type-body1-strong); border-radius: var(--radius-medium);
  height: 32px; padding: 0 14px; display: inline-flex; align-items: center; gap: 6px;
  border: 1px solid transparent; cursor: pointer;
  transition: background var(--motion-normal) var(--ease-out);
}
.btn--primary{ background: var(--accent-rest); color: var(--fg-on-accent); }
.btn--primary:hover{ background: var(--accent-hover); }
.btn--primary:focus-visible{ outline: 2px solid var(--stroke-focus); outline-offset: 1px; }
.btn--secondary{ background:#fff; color: var(--accent-rest); border-color: var(--accent-rest); }

<!-- reuse anywhere, wire behaviour with Alpine -->
<button class="btn btn--primary" x-on:click="submit()">Submit request</button>

Input with focus state

.input{
  font: var(--type-body1); color: var(--fg-primary);
  background: var(--surface-input); border: 1px solid var(--stroke-control);
  border-radius: var(--radius-medium); height: 32px; padding: 6px 10px;
}
.input:focus{ border-color: var(--stroke-accent); box-shadow: 0 0 0 1px var(--stroke-accent); outline: none; }
.input[aria-invalid]{ border-color: var(--fg-danger); }

<input class="input" x-model="amount" placeholder="CAD $0.00">

Card — base, then add motion

.card{
  background: var(--surface-raised); border: 1px solid var(--stroke-divider);
  border-radius: var(--radius-large); box-shadow: var(--shadow-4);
  padding: var(--space-160) var(--space-200);
}

<!-- .lift is a system utility — hover-rise, reduced-motion safe -->
<article class="card lift" tabindex="0"> … </article>
Every class above ships in components.css — link it, don't re-implement. The utilities .lift, .imgph, and .reveal live in colors_and_type.css. For .reveal, add the one-line IntersectionObserver from advanced-ui-example.html to toggle .is-in.

Guardrails

Rules you can't break

The handful that matter most when you're translating a design into tokens. The full set is in the Reference and README.

Do

Reference semantic tokens — var(--accent-rest), var(--fg-primary) — for every value.

Don't

Hard-code #0079C1, padding:15px, or a hand-rolled shadow. If you typed a literal, you skipped a token.

Do

Keep blue interactive-only — buttons, links, focus, selected rows.

Don't

Paint surfaces, headers, or hero blocks blue. And BMO Red is logo-only — errors use var(--fg-danger).

Do

Use Segoe UI (the default stack), sentence case, H1–H3 Regular weight.

Don't

Add a second typeface, ALL-CAPS labels, emoji, or Bold H1–H3.

Do

Stay on white surfaces with subtle elevation; soft --surface-tint-* only for section bands.

Don't

Use gradients, heavy shadows, SharePoint's warm #F3F2F1, or a left-accent border on cards.

Build a screen — the loop

A repeatable order of operations for any new view.

  1. Link colors_and_type.css. Base elements are now correct; you have every token.
  2. Lay out with the spacing ramp + 12-column grid. Container padding 16–24px. Information-dense is correct here.
  3. Reuse a documented pattern for each element. Find it in the Reference, copy the markup, wire behaviour in Alpine.
  4. Apply only semantic tokens. No literals. Blue interactive-only, red logo-only.
  5. Add restraint-level motion if it earns it. .lift on actionable cards, .reveal on sections. Respect reduced-motion.
  6. Check copy against the tone rules. Sentence case, plain, numerals, no emoji. ../context/ → BMO brand + content.
  7. Diff against the Reference. When in doubt, the rendered Reference is the source of truth.
