Editorial design guide
Overview

The look, in plain language

Clean. Blue-dominant. Information-dense but well-organized. Professional without being cold. Grounded in Microsoft's Fluent 2 language, aware of the SharePoint shell it lives inside, and carrying BMO's brand character through controlled use of their signature blue and typographic clarity.

White surfaces. Segoe UI. Subtle elevation. A single blue family running through brand, shell, and component system. No decorative red. No heavy shadows. No consumer-facing playfulness.

On top of that restrained base sits a visual-interest layer: soft, low-saturation surface tints for alternating bands, functional motion (reveal-on-scroll and hover lift), labeled imagery placeholders, and a flexible card composition with interchangeable parts. It is additive — the plain white card with no motion is still the default. Reach for the richer treatment on landing and home surfaces where engagement matters.

How decisions are made

Three source layers

When two layers disagree, the lower-numbered layer wins.

LAYER 1 · AUTHORITY
BMO digital brand
Color values, type ramp, tone, and any rule that names BMO directly. The color authority.
LAYER 2 · ENVIRONMENT
SharePoint Online
Surface behavior, elevation budget, and how the app sits on the page. Don't fight the shell.
LAYER 3 · CONSTRUCTION
Fluent 2
Spacing ramp, corner radii, shadow ramp, type scale, motion. The default for anything not governed above.

The red rule

BMO Red — #ED1C24
Logo · marketing roundel only

Reserved for the M-Bar roundel, BMO red marketing circle, secure sign-in button on external sites, and the focus state of inline hyperlinks. Not a UI color.

Negative — #D12121
Errors · destructive · negative data

All red in app UI uses this token. Matches Fluent 2 semantic red (#D13438) closely enough that the two systems agree.

Adding red to a layout does not make it more on-brand. Use one red per screen at most, and only if it's the logo or a real error.

Motion — new

Functional, not decorative. Fluent 2 curves and durations, exposed as tokens. Content reveals once and settles; cards lift on hover; nothing loops, bounces, or springs. prefers-reduced-motion is always honored.

Duration + easing tokens

--motion-fast100 msInstant color / border shifts
--motion-normal160 msHover lift, arrow nudge
--motion-slow250 msPanel / dialog entrance
--motion-reveal550 msReveal-on-scroll fade + rise
--ease-out / --ease-in / --ease-in-outcurvesOut = entering, in = exiting, in-out = movement

Patterns

Hover lift
Hover me — rise 3 px, deepen to shadow-16
.lift · 160 ms ease-out
Reveal on scroll
Fade + rise 14 px once, then settle
.reveal · 550 ms ease-out
Arrow nudge
Link arrows slide 3 px on hover
transform · 160 ms ease-out
Reduced-motion safe by construction. The .reveal hidden start-state only exists inside @media (prefers-reduced-motion: no-preference), so print, no-JS, and reduced-motion users always see full content. In app mode .reveal is transition-based — JS adds .is-in on scroll to play it.
Editorial mode reveals the same class differently. Under the .editorial scope, .reveal is a self-sufficient CSS animation that plays on load with no script (one less load-bearing dependency). It reuses the same --motion-reveal / --ease-out / --reveal-rise tokens and honors reduced-motion, and the same .is-in short-circuits it to instantly-visible — so the two mechanisms coexist by scope + specificity without colliding. Content

Voice & tone

Direct, plain, human. The app speaks to the user, not about them. Active voice. Numerals for numbers. Sentence case everywhere.

Do
Submitted. Approval is pending with Sarah Chen.

Calm statement of fact + the next thing the user wants to know.

Don't
Awesome — you're all done! 🎉

Consumer-y. Apologetic or congratulatory tone is wrong for financial work.

Do
Review the Q3 expense policy →

Meaningful keyword anchors the link. Direct what comes next.

Don't
Click here to read more

Per BMO + Fluent 2 guidance: never "click here" or "read more".

Do
We couldn't save your changes. Try again.

Plain explanation + clear next step. No apology, no "oops".

Don't
Oops! Something went wrong.

"Oops" is a consumer cliche. Generic messages don't help the user.

Visual do's and don'ts

Do

Use white surfaces with subtle shadow-4 for cards. Use 1 px #D9DCE1 dividers for structure.

Don't

Use heavy drop shadows or floating cards with deep elevation on embedded surfaces.

Do

Fill the primary button with Accessible Blue. Pair with a white-filled secondary that shares the same border.

Don't

Paint card headers, banners, or empty-state hero blocks blue. The SharePoint suite bar already carries strong blue.

Do

Use Fluent System Icons inline as SVG. Single colour fill, sized 12 / 16 / 20 / 24 px only.

Don't

Use emoji, unicode symbols, or icons from a different family. Don't scale icons to arbitrary sizes.

Do

Lean into information density. Tables, lists, data grids are correct for financial productivity tools.

Don't

Pad screens to feel "airy" or replace data tables with decorative card grids.

Do

Use one red per screen, and only if it's the logo or a real error using #D12121.

Don't

Use BMO Red as a decorative accent, category badge, or to "make a layout more on-brand".

Do

Separate sections with soft surface tints (--surface-tint-*), alternating tint / white. Keep interactive surfaces on white.

Don't

Use gradients, saturated fills, or tints behind buttons, inputs, and cards. A tint is a ground, not a highlight.

Do

Reveal content once on scroll and lift cards 3 px on hover. Honor prefers-reduced-motion and keep base states visible.

Don't

Loop, bounce, spring, parallax, or auto-play decorative motion. Motion is a cue, not entertainment.

Do

Use labeled .imgph placeholders that name the asset and size until real photography or line art is licensed.

Don't

Drop in glossy stock imagery, or leave an empty grey box with no indication of what belongs there.
